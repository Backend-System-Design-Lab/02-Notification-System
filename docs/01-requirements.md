# 01. Requirements

## 1. 문제 정의

여러 서비스에서 발생한 이벤트를 사용자에게 Push, SMS, Email로 전달하는 알림 시스템을 구현한다.

이번 프로젝트에서는 다음 문제에 초점을 맞춘다.
- 높은 트래픽에서도 알림 요청을 안정적으로 처리할 수 있는가?
- 외부 알림 서비스의 지연이나 장애가 전체 시스템에 영향을 주지 않도록 할 수 있는가?
- 실패한 알림을 재시도하면서 데이터 유실과 중복 전송을 최소화할 수 있는가?

## 2. 사용자 및 사용 시나리오

### 주요 사용자

- 사용자 유형: 알림을 요청하는 내부 서비스, 알림을 수신하는 사용자
- 주요 채널: Push, SMS, Email 
- 사용 환경: iOS, Android, Web/Desktop
- 한 사용자는 여러 단말을 등록할 수 있다.

### 핵심 시나리오

1. 내부 서비스가 알림 전송을 요청한다.
2. 시스템이 사용자 정보와 알림 설정을 확인한다.
3. 활성화된 채널로 알림을 전달한다.
4. 실패하면 재시도하고 최종 실패를 기록한다.

## 3. 기능 요구사항

| ID | 요구사항                                     | 우선순위 |
|---|------------------------------------------|------|
| FR-001 | Push, SMS, Email 알림 요청을 처리한다.            | Must |
| FR-002 | 사용자별 Email, 전화번호와 여러 Device Token을 관리한다. | Must |
| FR-003 | 사용자별 채널 알림 On/Off 설정을 지원한다. | Must |
| FR-004 | 템플릿을 이용해 알림 메시지를 생성한다. | Must |
| FR-005 | 실패한 알림을 재시도하고 최종 실패를 관리한다. | Must |
| FR-006 | Event ID를 기반으로 중복 요청을 방지한다. | Must | 
| FR-007 | 사용자 또는 서비스별 전송률을 제한한다. | Should | 
| FR-008 | 알림 처리 상태와 전송 결과를 기록한다. | Should |

우선순위 기준:

- Must: 반드시 구현
- Should: 가능하면 구현
- Could: 여유가 있을 때 구현
- Won't: 현재 범위에서 제외

## 4. 비기능 요구사항

### 성능

- 연성 실시간(Soft Real-Time)방식으로 가능한 빠르게 전달한다.
- 높은 부하에서는 일정 수준의 전달 지연을 허용한다.
- 목표 트래픽과 Peak RPS는 용량 산정 단계에서 계산한다.
- API 오류율 목표는 1% 미만으로 한다.

### 가용성 및 안정성

- 수락된 알림이 서버 장애로 유실되지 않아야 한다.
- 외부 Provider 장애가 전체 알림 시스템 장애로 전파되지 않아야 한다.
- 실패한 메시지는 재시도하고 반복 실패는 별도로 관리한다.
- 알림 서버와 Worker는 수평 확장할 수 있어야 한다.

### 정합성

- 기본 전달 방식은 At-least-once를 목표로 한다.
- Event ID 기반 멱등성 처리로 중복 알림을 최소화한다.
- 사용자 정보와 알림 설정은 DB를 기준 데이터로 사용한다.

### 보안

- 인증된 내부 서비스만 알림 API를 호출할 수 있어야 하낟.
- Email, 전화번호, Device Token과 같은 개인정보를 보호한다.
- 개인정보 전체 값을 애플레킹션 로그에 기록하지 않는다.

## 5. 범위

### 포함

- Push / SMS / Email 알림
- 사용자 연락처 및 다중 Device 관리
- 알림 설정 및 템플릿
- 메시지 큐 기반 비동기 처리
- Retry / DLQ / 중복 방지
- Rate Limit
- Mock 외부 Provider
- k6 부하 테스트 및 Prometheus/Grafana 모니터링

### 제외

- 실제 APNs, FCM, SMS, Email 유료 서비스 발송
- 실제 모바일 애플리케이션 개발
- Kubernetes 및 다중 리전 구성
- 실제 대규모 운영 환경 구축

## 6. 성공 기준

- [ ] 세 가지 채널의 알림을 처리할 수 있다.
- [ ] 외부 Provider 지연과 장애 상황을 재현할 수 있다.
- [ ] 메시지 유실 방지와 실패 재처리 구조를 검증한다.
- [ ] 동일 이벤트의 중복 처리를 방지한다.
- [ ] 동기식 구조와 비동기 구조의 성능을 비교한다.
- [ ] Queue 적체와 Worker 처리량을 관측할 수 있다.
